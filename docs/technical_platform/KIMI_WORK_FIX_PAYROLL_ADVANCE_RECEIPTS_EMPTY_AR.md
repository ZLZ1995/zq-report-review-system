### 1.3 应收账款空壳行

初步责任：页面状态和写入/清理生命周期缺少原子性守卫。

## 2. 对原方案的必要修正

### 2.1 不允许“职工薪酬不相等就回退单行并继续发布”

如果9个叶子科目合计与BS不一致：

- 保留来源行和差异证据；
- 输出lineage和reconciliation失败报告；
- 阻断正式发布，保留上一版交付件；
- 只有当Skill明确允许`placeholder_only`总额站位时，才能生成“总额已核实、明细待补”状态，且不能伪装成`detail_fillable`。

不得用“应付职工薪酬”单行覆盖真实明细后宣称成功。

### 2.2 不允许为预收账款追加合成调节行

Skill明确禁止用平衡行、调节行或技术标签替代真实来源明细。正确规则是：

- 真实TB/客商/序时账来源行永远优先保留；
- 差额进入`unreconciled_reasons.json`、`field_lineage_report.json`和用户反馈；
- 差额阻断完整交付，不能变成新的会计明细行；
- 不覆盖已有真实户名、业务内容和发生日期。

### 2.3 职工薪酬日期不得无条件伪造为月末

先核对模板填表说明和人工基准的日期口径：

1. 如果模板明确规定累计余额行使用报告期末日，允许使用`report_date`，但必须记录`date_source=reporting_date_policy`及来源单元格；不能把`2026-07-31`写死在通用代码中。
2. 如果字段含义是“最后实际发生日期”，必须按2211叶子科目从序时账选择最后一笔真实贷方业务日期。
3. 如果没有可证明的日期，不得猜测；留空并记录evidence boundary，或按当前项目门禁阻断。

人工基准可以证明预期呈现，但不能单独把虚构日期变成会计事实。

### 2.4 预收账款B列语义必须先核对

如果B列标题为“户名/结算对象”，`销项税暂估`通常是业务或税务标签，不是公司、个人或明确法律主体。实施前必须核对：

- 模板B/D列实际表头；
- 人工基准B6、C6、D6的具体值；
- TB辅助核算对象；
- 序时账中的对方科目、客商和摘要。

期望规则：

- B列只写来源证明的真实主体；
- C列写来源证明的发生日期；
- `销项税暂估`应写入业务内容/子科目列，而不是为了对齐人工基准强塞户名列；
- 如果人工基准确实采用项目级特殊口径，必须记录为显式项目规则，不能固化为所有项目的全局规则。

### 2.5 空表不能只做“跳过写入”

若页面为空：

- `not_in_scope_hide`：不改页体，完成结构检查后隐藏；
- `zero_balance_cleanup`：只清理确认可写的数据体输入格，包括遗留序号A6，保留标题、公式、合并、页脚、超链接；
- BS非零但明细为空：不能当作普通空表，必须进入`placeholder_only`或阻断状态。

这样才能既消除A6空壳行，又避免return后保留旧项目残留。
